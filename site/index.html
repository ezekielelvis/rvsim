A deterministic RISC-V full-system emulator

The same run, every single time

rvsim boots real Linux on an emulated RISC-V computer. Give it the same images and the same keystrokes and it executes the same instructions in the same order, on any machine. So a bug seen once can be replayed, traced, debugged backwards and broken on purpose.

How it works

A fast core and a careful monitor

rvsim is split along one line. Everything that happens on every instruction lives in a C++ core. Everything that happens now and then, like a device access or a timer firing, lives in a Go virtual machine monitor (VMM). They never talk per instruction.

  1. 1

    The VMM sets a deadline

    It works out how many steps remain until something must happen: the next timer event, checkpoint, keystroke or fault. Then it calls rv_run(budget).

  2. 2

    The core runs flat out

    Decode, execute, translate addresses through the Sv39 page tables, take traps. About 60–70 million instructions a second, with no calls back into Go.

  3. 3

    It stops and says why

    When it needs help, or the budget runs out exactly, the core returns an exit. The VMM handles it and starts the next pass. A round trip costs about 130 ns.

Four exits

Every reason the core stops

Device access

RV_EXIT_MMIO_READ / WRITE

A load or store hit the UART, interrupt controller or disk. The VMM performs it; the core re-runs the instruction with the result.

Idle

RV_EXIT_WFI

The guest ran wfi with nothing to do. Virtual time skips to the next event instead of spinning through it.

Breakpoint

RV_EXIT_BREAKPOINT

The pc reached an address GDB asked to stop at, before the instruction runs.

Deadline

RV_EXIT_BUDGET

The budget is spent, exactly on the step where an event, checkpoint, keystroke or fault is due.

Virtual time

Time is counted, never read

Most emulators ask the host for the time, and that is where two runs drift apart. rvsim never reads a clock. Its clock is a count of steps: a retired instruction, a taken trap, or one unit of idle time skipped during wfi. The timer Linux sees ticks once every 10 steps at a nominal 10 MHz, so one guest second is 100 million steps. Keystrokes enter only between steps and are stamped with the step they arrived at.

Record and replay

Record once, replay forever

A recording only needs the inputs: the images' hashes, each typed byte with its step, and every 10 million steps a hash of the core, all of RAM and the devices. The eight-second session above fits in 4,424 bytes.

Replay feeds each byte back at its step and checks every hash. Nobody is typing, so it finishes in under two seconds. CI records on Ubuntu and replays on macOS.

Divergence reports

When a replay doesn't match, it says where

To show one, I changed a single recorded keystroke: free -m became free -k. Every checkpoint before that byte still matches. The first one after it fails, and rvsim names the 10-million-step window where the state split and the command to trace it.

Tracing

Look at any instruction

rvsim trace replays a recording and logs a window of steps in the format of Spike, the RISC-V reference simulator. CI runs programs in both and compares them instruction by instruction.

Snapshots

Save the machine, come back later

A snapshot is the whole computer at a step: registers, 256 MiB of RAM, every device, pending timer events and the disk. Empty pages are skipped and the rest compressed, so a booted Linux is about 4 MB. Restoring continues exactly as the original run would have.

Replays can drop snapshots as they go. Then reaching any step means restoring the nearest one and running forward: 0.09 s to step 700 million.

Reverse debugging

Debug the kernel, backwards too

rvsim speaks GDB's remote protocol, so stock GDB with the kernel's symbols can set breakpoints, read registers and memory through the guest's page tables, and walk the stack.

On a recording it also goes backwards. Any step can be reached exactly, so reverse-stepi restores a nearby snapshot and runs forward to one step earlier. Here GDB stops as the kernel starts /init, steps forward five instructions and back five.

Fault injection

Break things on purpose

Hardware fails rarely and at random, so the code that copes with failure is hard to test. A small YAML file can flip RAM bits, corrupt registers, return wrong device values, drop or delay interrupts, fail disk requests or garble serial bytes. Faults fire at an exact step, pc, instruction count or device access, or with a seeded probability, and they are recorded, so a faulty run replays exactly too.

With 2% of console bytes garbled, the shell echoed fox as wox, yet the command's own output came through clean.

Fault injection

Four lines of YAML, one kernel panic

This spec waits for the pc to reach kernel_execve and sets its filename argument to NULL. Linux measures the name with strlen, reads address zero and dies, at step 67,038,275 on every run. The crash can be replayed, traced and stepped through as often as needed.

The faulting instruction, strlen+0x6, is the same one the trace above caught reading a healthy string.

Try it

From clone to a Linux shell

You need Go 1.26 or newer, CMake 3.24+, a C++20 compiler, and Podman or Docker to build the Linux images. The first image build is slow: it compiles a toolchain, OpenSBI, Linux and BusyBox in a container.

  1. 1

    Build

    git clone https://github.com/ezekielelvis/rvsim
cd rvsim
make go-build
make images
  2. 2

    Boot

    bin/rvsim boot \
  -firmware build/images/fw_jump.bin \
  -kernel build/images/Image \
  -initrd build/images/rootfs.cpio

    Type poweroff to leave.

  3. 3

    Record and replay

    bin/rvsim record -o s.rvrec \
  -firmware … -kernel … -initrd …
bin/rvsim replay s.rvrec
  4. 4

    Debug or break it

    bin/rvsim replay -gdb localhost:1234 s.rvrec &
gdb-multiarch build/images/vmlinux \
  -ex 'target remote localhost:1234'
bin/rvsim boot -faults \
  docs/faults/flaky-console.yaml …
